# Architecture decisions

1. **Modular monolith:** one Java process and one PostgreSQL database. Clear safety boundary, transactions across ownership/outbox, few operational dependencies. The tradeoff is shared deployment/failure scope. No Kafka, Redis, or Kubernetes is needed for this assignment.
2. **Java 21 / Spring Boot 3.5:** mature REST, validation, JPA, JDBC transactions, scheduling, JUnit, and Testcontainers. Java 21 is explicitly selected in verification and CI. Startup/memory are larger than a small Go service.
3. **SQL for critical writes; JPA for reads:** exact lock clauses and partial indexes are visible. This makes concurrency more reviewable than implicit ORM flush order, at the cost of explicit SQL and fewer generic repositories.
4. **Campaign serialization:** a row lock surrounds capacity observation and actual allocation. Approval is not a reusable token that can be double-spent. Hot campaigns serialize; partitioning is a future change requiring an explicit capacity-credit protocol.
5. **Outbox and leases:** no network calls in the allocation transaction. Durable dispatch plus provider-side stable idempotency closes the crash window. Lease expiry is not evidence that an external call stopped.
6. **Durable provider simulation:** provider records are independently committed before latency or ambiguous timeout. Both mocks implement the same interface; B adds duplicates, delayed responses, and event disorder. Storage is shared physically for convenience, but transaction boundaries represent external acceptance.
7. **Conservative statistical safety:** use a simple binomial bound with an elevated answer probability, hard campaign limits, bounded speculative exposure, and fallback. This can sacrifice the utilization benefit. It is not a zero-abandonment proof under correlated behavior.
8. **Terminal evidence wins:** event order is not trusted, so a completion closes ownership even if answer evidence is missing. Late events cannot resurrect a call. Historical answer metrics can undercount after disorder; audit evidence remains available.
9. **Virtual-clock simulation:** seconds advance deterministically with a seeded PRNG. Both modes share policy classes and use the same initial seed and configured conditions. Different admission sequences consume different random draws; this is not per-borrower paired experimental control.
10. **Polling dashboard:** same-origin Next.js rewrites avoid CORS and a three-second poll is sufficient here. Snapshot queries are bounded; a production monitoring read model would reduce repeated scans.
11. **Local-only prototype:** no real borrower data, numbers, telecom credentials, remote publish, or GitHub push. Authentication, webhook signatures, retention, and hard cancel are intentionally future work, documented explicitly.
